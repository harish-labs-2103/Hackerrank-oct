# Evaluation report — Data Investigator

## Methodology

- **Labelled set:** the 32 public requests in `dataset/sample_deletion_requests.csv`, scored against
  `dataset/sample_output.csv` by `python code/evaluation/main.py`. The same `Session` (dataset
  loading, evidence index, identity graph, guarded LLM, engine) is used as for the full run, so
  the score reflects the shipped pipeline.
- **Metrics** (`code/davestigator/scoring.py`):
  - *case-level status accuracy*: `deletion_status` equal to gold;
  - *exact row*: status and the whole `steps_json` equal (step_no, phase, system, resource,
    operation, state, evidence);
  - *step precision / recall / F1*: steps matched on (operation, system_id, resource_id);
  - *evidence-ID accuracy*: on matched steps, `evidence_id` equal to gold;
  - *field-level accuracy*: gold step *i* vs predicted step *i*, per field (positional, so a
    missing early step shifts later fields — a strict measure of sequence fidelity);
  - *sequence accuracy*: identical ordered list of (operation, system, resource).
- **Custom cases:** 7 team-authored miniature datasets in the challenge formats (fictional people,
  `code/evaluation/custom_cases/*/dataset`, expected answers in `expected_output.csv`), rebuilt by
  `python code/evaluation/build_custom_cases.py`. They target failure modes the public samples
  under-represent: replica drift, sync recreation, tombstone hashes, multilingual non-deletion,
  post-audit evidence, prompt injection inside evidence, and a near-duplicate-email decoy.
- **Full-set checks without labels:** contract validation of all 518 rows; cross-check of
  `NOT_APPLICABLE` decisions against the intake system's independent `CLASSIFY_REQUEST
  non-deletion` activity rows (which the classifier never reads): **10 of 10 match**; and the
  LLM-influence diff (deterministic vs LLM-assisted).

## Failures found and improvements made

Chronological, each found by the sample score, the validator, a test, or the full-set checks.

| # | Failure observed | Root cause | Change | Effect |
|---|---|---|---|---|
| 1 | Evidence ids on matched steps 85% correct; e.g. `evidence_02` cited where gold has `evidence_92`. | State was taken from any observation stamped before `audit_at`, including a bundle exported 2 days *after* the audit. | State and citations use only sources whose manifest `captured_at` ≤ `audit_at`. | Evidence-ID accuracy 85% → 100% on samples. |
| 2 | `case_26` predicted `NOT_APPLICABLE` (gold `COMPLETE`). | "Confirm that the profile is gone" has no delete verb. | Requests to verify a completed deletion count as deletion intent. | Status accuracy 90.6% → 93.8%. |
| 3 | `case_17` had an extra account (`account_6523`). | Linked by a lookup 163 days before the request — an earlier episode. | Link window `[requested_at − 1 day, audit_at]`; on samples every gold link falls inside it. | Precision 98.1% → 99.4%. |
| 4 | Validator blocked the first full run: 22 findings cited files captured after `audit_at`, 9 `COMPLETE` verifications had no evidence. | Same as #1 for log lines inside later exports; unknown-state resources were emitted as verifications. | Later exports may *link* a resource but never prove its state; an unproven state is a reported gap, never a verification. | Valid 518-row output. |
| 5 | Accounts in many `COMPLETE` eval cases had no admissible state (only a 404 in a later log). | Absence was only recognized from explicit 404/NOT_FOUND. | Full-scope inventory snapshots (`snapshot_scope`) that captured the subject's other records but no profile prove `ABSENT`. | Eval obligations with no established state fell from 168 to 140 (mostly accounts in COMPLETE cases); samples unchanged. |
| 6 | Rule #5 first version flipped `case_05` to `COMPLETE`. | An *empty* scope-only snapshot (`evidence_90`) was treated as proof. | Coverage counts only when the snapshot also captured this subject's records. | `case_05` back to `INCOMPLETE`. |
| 7 | `case_539` ("information request, not a request to erase it") classified as deletion. | Negated deletion verb. | Negation patterns in the heuristic and in the LLM-override cue. | 10/10 `NOT_APPLICABLE` match the intake system. |
| 8 | Unit test: cloud-runtime log lines lost the first key inside `message="k=\"v\" ..."`. | Outer `message=` consumed the inner key. | Parse the escaped inner payload separately. | All 6 log dialects parse in tests. |
| 9 | Gemma 3 4B misread a full screenshot (`jain.aditi` → `join.andri`, `data_flow_9846` → `data_flow_8866`) and attached emails to the wrong row. | 1800-px screenshot downscaled; table rows dense. | Two crops per screenshot; guard keeps only resource ids grounded elsewhere and identifiers known to the identity graph; screenshot identifiers never create links (state + name-conflict only). | Misreads cannot become findings (HAL-01/02/12). |
| 10 | A catalog link (`marketing_001` → subject) contradicted by the record's screenshot showing a different person. | Activity links are claims. | If the record shows a person name that is not the subject's, the link is dropped and reported as a gap. | Never merges different people. |
| 12 | First full LLM run: the guard log showed the model emitting the *example ids written in the extraction prompt* (`search_45`, `marketing_1`, `object_19`, `tombstone_17`, …) for unrelated screenshots. 23 were rejected as ungrounded, but `object_19` and `tombstone_17` exist in the catalog and were accepted for 3 wrong screenshots. | Prompt contained concrete identifiers; a 4B model copies them. | Prompt v2 describes the id *shape* only; a test fails if any prompt contains a resource id, user ref or email. Catalog aliases (`object_19 (delivery_confirmation_19.pdf)` — "confirmed" rows were not parsed before) now map file names to ids. | v2 accepts 13 rows, each its own screenshot's resource, 0 echoes. v2 also showed a fused label `user_20_analytics_7438`; the guard now accepts a label holding exactly one embedded id — this corrected case_50, which v1 had wrongly verified as anonymized (v1 had lost the name/email). ## Remaining limitations

- **Unlinkable records.** Some gold resources carry no identifier in any participant-visible
  evidence (fully anonymized analytics profiles; profiles whose only trace is a deletion-worker row
  without subject; a few audit records absent from all files). These account for nearly all missed
  sample steps (step recall ≈ 84%, precision ≈ 99%). The engine does not guess them.
- **Hand-written sample cases 01–10** use conventions that do not recur in the generated set
  (e.g. a legacy contact-index support row expected to be deleted). Not special-cased.
- **Screenshots** depend on a 4B vision model on CPU; anything it misreads is dropped by the guard,
  so a screenshot can at worst contribute nothing.
- Absence is inferred only from explicit lookups and full-scope inventory snapshots that captured
  the subject; partial snapshots are never read as "absent".
